# JavaScript module refactor review

Reviewed 2026-09-28 against the working tree. This is a recommendation only; no application or test code was changed. The worktree already had unrelated modifications, so sizes and observations describe the files as read and may move while other work continues.

## Scope and architecture

“Large” here means at least 400 physical lines **or** 30,000 bytes. The inventory covers every first-party `src` JavaScript file meeting either threshold and the one test file that does. Sizes are approximate, rounded from the working-tree snapshot. The three minified third-party files under `src/shared/vendor/` are listed separately below. Smaller dependencies appear where they define an extraction boundary.

The main application is loaded by 55 ordered `<script src>` tags in [index.html](src/program-planner/index.html). Most files publish APIs on `window.UOS`; `nsa.html` and `events.html` iframe this same entry point with different owner parameters. Several controllers also register DOM-ready and `uos:program-ready` listeners when evaluated. Any extraction must preserve script order, public `UOS` names, event payloads, and the NSA/EVT owner behavior until consumers are migrated deliberately. A wholesale module-system conversion is not a useful first slice.

## Coupling risks to control

1. **Global load order and eager side effects.** [index.html](src/program-planner/index.html) loads `ProgramModel` before `ProgramCosting`, `WorkAreaService`, `ProgramQuotes`, and UI controllers, then loads `ProgramApp` near the end. Several controllers bind on evaluation or DOM ready. Moving a helper to a new file without inserting it before its first consumer can fail only in the browser; CommonJS-style unit loads do not prove the script chain works.
2. **One canonical workspace, several local UI states.** `ProgramApp.updateWorkspace` clones, normalizes, serializes mutations, saves, and publishes `uos:program-ready` plus `uos:workspace-changed`. `ProgramMapController.persistCanonicalMapState` deliberately skips unchanged writes to avoid a ready/render/save loop. Register selection writes IDs into planner, costing, scheduler, map, and inspector state. Split these paths around a single mutation/selection contract or stale IDs and duplicate renders can reappear.
3. **Durability spans two files.** [program-planner/js/storage.js](src/program-planner/js/storage.js) (below the size threshold) controls revision semantics and read-back verification; [shared/js/storage.js](src/shared/js/storage.js) performs atomic IndexedDB commit/lease checks. A refactor of either one alone can break revision fencing, last-verified recovery, or multi-tab read-only behavior.
4. **Spatial and commercial lineage crosses models.** `RemediationModel` measures and repairs shapes; `RemediationMap` edits them; `ProgramMapController` adapts them; `WorkAreaService` measures canonical work geometry and creates/syncs mapped cost lines; `ProgramCosting` and `ProgramQuotes` consume those lines. Treat geometry, rate mapping, job lineage, and quote lock rules as connected contracts. Similar math in these files is an extraction candidate, not evidence that the implementations can already be interchanged.
5. **Multiple serialization surfaces.** `ProgramData` and `unifiedWorkspace` both contain ZIP/CSV machinery, but their bundle identity, owner slicing, limits, and legacy adapters need comparison before reuse. Cross-owner import isolation and preview-before-apply are behavioral boundaries, not helper details.
6. **Cross-view DOM ownership.** Register, map, planner, scheduler, costing, quote builder, disclosure rows, and status UI all respond to workspace or click events. Moving a listener or card enhancer can duplicate handlers, break drawer focus/scroll, or mask status/privacy state. Define which controller owns each view and event before splitting render functions.

## Ordered recommendations

1. **Freeze observable contracts first.** Add focused characterization fixtures for `UOS` API names, ordered browser bootstrap, event details, canonical workspace snapshots, import/export bytes or parsed equivalence, and owner entry points. Record current behavior from the existing suite before altering internals. Preserve the current global facades throughout incremental extraction.
2. **Extract the pure business seams.** Start with `ProgramModel` migrations/validators/lineage, `RemediationModel` geometry and allocation, `WorkAreaService` measurement/rate resolution, `ProgramCosting` arithmetic, and `ProgramQuotes` lifecycle/payment arithmetic. Have controllers call the existing facade until callers are migrated. Gate each slice on schema-v1–v5, cost-line, quote, and deletion invariants.
3. **Define the workspace transaction boundary.** Isolate the queue/commit/event policy in `ProgramApp` together with the revision/recovery interface of `ProgramStorage` and `UOS.storage`. Keep the IndexedDB revision comparison, canonical write, and pending-verification marker in one transaction. Gate on simultaneous edits, failed saves, lease takeover, read-back, and exactly-once event publication.
4. **Separate map selection from map rendering.** Move pure map-state and dataset/filter logic out of `program-map.js`, then separate `RemediationMap` basemap lifecycle from drawing interactions. Keep WKT/GeoJSON parsing at an import boundary. Gate on register/project selection, owner switches, repeated render idempotence, geometry edit/cancel/undo, provider failure, and measured job quantities.
5. **Split feature controllers along view and command lines.** For Register, Quote Builder, Costing, Scheduler, and Planner, put selectors/view-models and workspace commands behind small APIs before moving DOM renderers. Keep disclosure/motion and lifecycle dialog focus under one owner. Avoid simultaneous rewrites of the same card or event path in multiple controllers.
6. **Consolidate data exchange only after format comparison.** Extract `ProgramData` staging/identity checks and a bounded archive codec; compare it with `unifiedWorkspace` using golden JSON/ZIP/CSV fixtures. Reuse codec code only where headers, safety limits, and outputs match; keep application-specific migration and promotion policy separate.
7. **Finish with low-risk infrastructure cleanup.** Split `suite.js` services and `governed-remediation.test.cjs` by domain once integration tests cover initialization and governance IDs. Keep `product-contracts.js` declarative unless rule churn, rather than file length, justifies another module.
